# Discipline — feature spec(s)

Moved verbatim from root `CLAUDE.md`'s Feature Flags table. Root keeps a one-line summary + `→ full spec:` pointer here. Default column below matches `DEFAULT_COMPANY_FEATURES` in `server/app/core/feature_flags.py`.

## Discipline (moved from root Key Modules)

- **Discipline** (`matcha/routes/employee_lifecycle/discipline.py` + `services/discipline/discipline_engine.py`, signature provider abstraction in `services/signature_provider.py`). Two AI/legal layers sit on top of the deterministic escalation ladder, and the split between them is load-bearing:
  - **Compliance gate** (`services/discipline/discipline_compliance.py`, migration `discipcomp01`) — **deterministic, no LLM**. Records now carry `occurrence_dates` (when the conduct happened, distinct from `issued_date`); the gate tests them against the employee's approved `leave_requests` (`fmla`/`state_pfml`/`medical`) + sick `pto_requests`, and consults a **curated, individually-cited** `_STATE_SICK_LEAVE_PROTECTIONS` table keyed on `employees.work_state`. Attendance infraction + protected-leave overlap + mapped state ⇒ **hard block**: `POST /discipline/records` 422s and there is **no override path** (a statute isn't a judgment call — following the attendance policy doesn't cure it; this is the CA Lab. Code § 246.5(c) case). Everything softer is an **advisory** requiring `advisory_ack_reason` (409 until supplied). Two invariants mirror `limit_adequacy`: **unmapped state ⇒ advisory, never "clear"** (the table is deliberately partial; add rows only with a real citation, never by inference), and **non-attendance conduct on a leave day ⇒ advisory, not block** (the statutes bar counting the *absence*, not shielding the person). The verdict is frozen on the row (`compliance_check` JSONB) **and** audit-logged in the same transaction as the insert. `GET /discipline/compliance-check` is a live FE **preview only** — `POST /records` always re-runs the gate server-side.
  - **Letter drafting + soft-risk review** (`services/discipline/discipline_ai.py`) — Gemini, grounded on a cid-indexed corpus (prior discipline, policy mapping, recent protected leave, the statute row) with hallucinated citations dropped by the shared `legal_defense.validate_citations`. `POST /discipline/ai/draft` turns an HR narrative into editable `description`/`expected_improvement`; at issue time a second pass flags documentation gaps/pretext-y tone as advisories. **The LLM never decides legality** and a Gemini outage degrades to one advisory — the gate already ran without it.
  - **Incident-triggered discipline + HR approval** (migration `discipapp01`) — closes incident→discipline end to end, driven by the `huume` Huume skill (see that flag's row) but readable from the discipline product itself. `progressive_discipline` gained `approval_status` (`not_required`/`pending`/`approved`/`denied`/`changes_requested` — the last added by `discipapp02`, see below — default `not_required` — every existing/direct-issue record is unaffected) + `source_incident_id`/`template_id`/`pending_remedial_requirement_id`. **`transition_status` is the single choke point**: its WHERE clause refuses any transition while `approval_status` is `pending`, `denied`, or `changes_requested`, so all 6 existing status-changing routes (meeting-held, signature refuse/upload, both webhook branches) 409 on a record still awaiting approval — this is enforced once in the engine, not re-implemented per route. Remedial training named on a `pending` draft is **staged** (`pending_remedial_requirement_id`), never assigned, until `POST /discipline/records/{id}/approve` (`discipline_engine.approve_record`, which assigns it, MOVES the id into `remedial_requirement_id` clearing the staged column, then transitions `draft → pending_meeting` — approval IS the issue step). `POST .../deny` (`DenyRequest`, ≥20-char reason) takes a `disposition` (`'reject'` default | `'revise'`) — **`reject` is terminal, no un-deny**; `revise` (migration `discipapp02`) sets `approval_status='changes_requested'` and leaves `status='draft'`, making the record editable via `PATCH /discipline/records/{id}` (`discipline_engine.update_draft_content`, allowlisted at the route's `DraftUpdateRequest` to `description`/`expected_improvement` only — NOT `discipline_type`/`severity`, since either would move the record's ladder position without re-running the escalation-ladder check or compliance gate that `POST /records` runs before insert; `update_draft_content` itself has no whitelist of its own, it trusts whatever `fields` dict the caller passes, so the Pydantic model is the only gate — guarded on `approval_status='changes_requested'`) and re-submittable via `POST .../resubmit` (`resubmit_for_approval` — back to `pending`, clears `approved_by`/`approval_decided_at`, leaves `denial_reason` in place as "what HR asked for" until the next decision overwrites it). The `deny_record` 'revise' branch itself does NOT stamp `approved_by`/`approval_decided_at` (only `reject` does) — the record hasn't been decided, it's been sent back. No new columns for any of this — the revise reason reuses `denial_reason`, and the round trail is `discipline_audit_log` rows (`approval_changes_requested`/`draft_revised`/`approval_resubmitted`). Approval also **stamps `advisory_ack_reason`** when the frozen `compliance_check` carried advisories: `POST /records` 409s until HR types one, and on this path HR approval IS the acknowledgment, so the column never sits NULL on exactly the records that had something to acknowledge (denial leaves it NULL — nothing was acknowledged). `GET /discipline/records/pending-approval` is the HR queue; `GET .../changes-requested` is the parallel "needs revision" queue (same static-path-before-`{discipline_id}` registration-order requirement — see the `TestRoutePendingApprovalDeclaredFirst`-style test for each). `services/discipline/discipline_policy_check.py` runs the (report-only, never-adjudicating) handbook/policy check a closed incident implicates, grounded via `handbook_pilot.gather_grounding`+`build_corpus`, citation-gated the same way `discipline_ai` is. `services/discipline/discipline_templates.py` resolves a company letter template deterministically (exact infraction+level → infraction-only → company default → scratch) and renders it over a closed placeholder vocabulary (unknown `{{token}}`s survive verbatim) — **the resolved template now reaches the filed letter, not just a preview**: the incident-triggered executor (`huume/discipline_skill.py::_execute_discipline_from_incident`) re-renders the template server-side into the persisted `description` (never trusts the staged `rendered_preview` string, which crossed a model turn), keeping the raw HR/model account in `situation_narrative`; `POST /discipline/ai/draft` additionally resolves+renders a template when one matches the (inferred) infraction type and returns it alongside the AI draft as `template_id`/`template_name`/`rendered_body`/`missing_fields` (additive keys — existing `description`/`expected_improvement` readers are unaffected). When no template resolves, both paths behave exactly as before (freeform text). `services/discipline/discipline_filing.py` files the signed letter on `employee_documents` (doc_type `discipline:<id>` — embeds the record id because the table's partial-unique index would otherwise collide a second letter for the same employee) and, when incident-triggered, on the incident's own Documents tab (`document_type='disciplinary'`). `clients.is_hr_approver` designates the approval-request audience (falls back to every business admin when nobody's designated) — a notification-targeting concern only, never an authorization boundary (`require_admin_or_client` still gates every route). `discipline_notifications.dispatch` gained an `audience` param (`all`/`hr_only`/`manager_only`/`drafter_only` — the last for the revise path, targeting `issued_by` and falling back to `hr_only` if that user is gone/inactive **or is the acting HR user who just denied the record** (`skip_user_id` — the common case, since `discipline_policy_sweep` opens the approval thread with the designated HR approvers, who then draft it themselves) — otherwise the record parks in `changes_requested` with nobody notified) alongside the pre-existing default. No queue table: the Celery `discipline_policy_sweep` (scheduler row seeded disabled) scans `ir_incidents` directly via SQL `NOT EXISTS` against its own one-row-per-incident ledger, so there is zero code at either incident-close site.
  - No new feature flag for the base module: all three layers ride the existing `discipline` flag.
