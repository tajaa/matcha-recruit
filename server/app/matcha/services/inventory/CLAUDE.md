# Inventory (channel-driven stock tracking) — feature spec

Moved verbatim from root `CLAUDE.md`'s Feature Flags table. Root keeps a one-line summary + `→ full spec:` pointer here. Default column matches `DEFAULT_COMPANY_FEATURES` in `server/app/core/feature_flags.py`.

## `inventory` (default ❌)

**Channel-driven inventory tracking** via `@huume` in any `/work` / `/werk` / `/werk-lite` channel — "we gifted some Cherry Farms cookies to Elizabeth our manager" auto-deducts stock; "we ran out of salads again" records a stockout, runs deterministic pattern math over the item's depletion history (`services/inventory/reorder.py:suggest_order` — daily consumption rate over a 90-day lookback, average stockout interval, confidence tier; returns `None` when history is too thin to say anything useful), and stages a pending order the manager approves by replying **confirm** in-channel. Like `ems`/`schedule_chat`, the `@huume` surface here is NOT the Huume thread agent (that requires an `mw_threads` row) — it's the EMS one-shot dispatch (`server/app/werk/routes/channels_ws.py`), routed by `services/ems/intent.py`'s `INVENTORY` classification (checked after `SCHEDULE`, before `RECALL`).

**Items auto-create on first mention for out/stockout only** — fuzzy-matched first (`services/inventory/matching.py`, stdlib `difflib`, no pg_trgm — deliberately avoided on RDS) so "cookies", "Cherry Farms Cookies!", and "cheery farms cookies" (typo) all resolve to the same row; a genuine miss inserts a new `auto_created=true` item. **Movements are an append-only ledger** (`inventory_movements`, kinds `out`/`in`/`stockout`/`adjust`) with exactly one sanctioned exception: a movement recorded with an unstated quantity ("some cookies") posts as `quantity=1, quantity_estimated=true` and arms a clarify question on the pill; a later numeric reply amends that SAME row in place (`amended_by`/`amended_at`, only while `quantity_estimated` is still true) rather than appending a correction — capped at 2 clarify rounds. `current_quantity NUMERIC NULL` on `inventory_items` means "unknown" (auto-created items start there); a deduction against an unknown count stays unknown, a `stockout` movement force-sets it to 0, and `adjust` (the only set-count path — always via `movements.adjust_item_count`, never a bare column write) establishes a real baseline.

**Provenance invariant for `kind='in'` (2026-08-04, amended 2026-08-05):** a received-stock movement is never written from a bare chat assertion — it comes from `orders.mark_received` (an open order being received), `receipts.commit_receipt_lines`/`receive_channel_lines` (a human-reviewed invoice), or **a chat-reported RETURN** (`kind='return'` in `extraction.extract_inventory`, the `_bg_inventory_request` `return` branch in `channels_ws.py`) — the one deliberate exception, added per product decision: a customer/patient/guest handing something back is a correction-scale event the reporter witnessed firsthand, same class as `adjust`, not a claim of an unverified delivery. The return branch still never auto-creates an item (`movements_service.find_item`, match-only — `find_or_create_item`'s insert path is NOT used here), so returning something never tracked steers to the Inventory page instead of minting a catalog row from an unreviewed claim. The written row's `note` always carries something — the reporter's own aside (`recipient_note`) or, absent one, a fallback `"Customer return (chat)"` — so a chat-return `in` row stays distinguishable in the ledger from an invoice/order-backed `in` row, which carries an invoice number or order linkage instead. **A return also DUAL-WRITES an EMS event** (`_bg_ems_intake`, same shape as the OSHA-keyword dual-write above and guarded so one message never fires it twice): a customer/patient handing something back is an interaction worth documenting, not only a ledger delta — the movement records the units, the event records what happened and why. The event fires on the unmatched path too, so documentation survives even when the stock write is refused. This closed two holes: the Huume thread tool `record_stock_movement` used to accept `kind="in"` and stage it like any other movement (now refused — see the Huume section below), and the channel `@huume` "receipt" classification used to call `record_movements(kind="in")` **immediately, with no confirm step**, auto-creating the item and defaulting an unstated quantity to 1 (now routed through `receipts.receive_channel_lines`, below). `out`/`stockout`/`adjust`/`return` stay free-form — consuming or crediting-back inventory the reporter directly observed is low-risk to get wrong; phantom *receiving* (a delivery that never happened) is what breaks the audit trail. Note `adjust` upward can still fabricate stock (a physical recount is inherently a bare assertion) — accepted, since it's a correction to a real count, not a claim of a delivery event.

Order lifecycle `queued` (staged from a stockout, or created manually on the Inventory page) → `ordered` (an in-channel **confirm** reply or a page Approve click) → `received` (a page Receive action, an in-channel delivery message checked in against the order — see below, or a committed receipt line) + `cancelled`. A partial unique index (`uniq_inventory_orders_open`) enforces one queued order per item; a repeat stockout re-points the SAME order's confirm pill (`orders.stage_order`'s `ON CONFLICT (item_id) WHERE status='queued' DO UPDATE`) rather than erroring or duplicating — the new system message becomes the order's `confirm_message_id`, so a reply to the earlier, superseded pill claims nothing and falls through to the mention fork (known/accepted v1 behavior).

**Channel "receipt" intake** (`extraction.extract_inventory` classifying kind="receipt", e.g. "we got the produce delivery") routes through `receipts.receive_channel_lines`, NOT `record_movements` directly: each line is matched against existing items (`matching.best_match`, same as `resolve_lines`) and, only if it has its own open order (`queued`/`ordered`, newest — two lines can't claim the same order, same dedupe as the receipts-page path), received against it via `orders.mark_received` inside a transaction. A line with no item match, no open order, an order already claimed, or an unstated quantity against an order that has none of its own is reported unmatched — no item is auto-created, no movement is written — and the pill (`pills.channel_receipt_pill`) steers the reporter to Receive Delivery on the Inventory page or to queue an order first. The old "estimated quantity + clarify pill" round-trip no longer applies to receipts (there's no order-less quantity to guess at); it's `out`-only now.

**Receipt ingest** (`services/inventory/receipts.py`, no vendor integration — a distributor invoice/packing-slip upload, not a POS or a direct Henry Schein/Patterson API; those are partner-gated and a later optimization, not v1) closes the `received` gap: before this, the only way to mark an order received was a human clicking Receive on the page and typing a count. Copies the SOV parse→review→commit triple (`routes/insurance/property.py` / `services/property/property_sov_parser.py`): `POST /inventory/receipts/parse` is best-effort and never raises — a `.csv` filename runs a deterministic `csv.DictReader` branch with NO model call, everything else (PDF/image) goes to Gemini as an inline `types.Part.from_bytes` with a line-items-only prompt (never invent quantities), falling back to `ERDocumentParser` text extraction — and returns a draft the caller reviews, writing nothing. `resolve_lines` fuzzy-matches each line against `movements.list_item_names` (`matching.best_match`, same engine channel intake uses) and attaches the ONE most-recent open order per item (`ORDER BY created_at DESC, id DESC` — `uniq_inventory_orders_open` only constrains `status='queued'`, so an item can carry several `ordered` rows too). `POST /inventory/receipts/commit` takes the user-EDITED lines — per line, its own `async with conn.transaction()` (one wrapping transaction can't survive a bad row; Postgres aborts the whole thing on the first error, same reason the CSV bulk-upload endpoints run row-by-row) — routing a line with an `order_id` through `orders.mark_received` (movement + order flip atomic together) and everything else through `find_or_create_item` + `record_movements(kind="in")`; bad lines land in `errors[]`, the rest still commit. A forceable 409 (`code: duplicate_invoice`, same family as a schedule conflict) blocks a second commit whose `invoice_number` already appears in a movement's `note` — no receipts table, so this is a text match, not a real index; `force=true` overrides it. **Units are deliberately NOT modeled**: the invoice's own `quantity`/`unit`/`pack_size` are shown verbatim on the review screen and the human confirms or edits the number that actually gets written — the same reason parse and commit are two separate calls, and the same limitation `unit conversion is not modeled` already documents below.

**Channel attachment ingest** (2026-08-05, `werk/routes/channels_ws.py:_bg_inventory_receipt` + `_bg_receipt_reply`): an admin drags an invoice/packing-slip into a werk channel and @huume's it — a CSV/PDF attachment is tried on a bare mention (nothing else said) or when the message text reads as a delivery/invoice mention (`_RECEIPT_TEXT_RE`), same wording bar a photo needs; a doc attachment on a non-bare, non-receipt-worded message ("@huume attaching the incident report from this morning" + a PDF) falls through to the normal intent fork instead of being claimed here, so it still reaches `classify_intent`/LOG and the OSHA dual-write. A photo is tried only when the message text itself reads as a delivery/invoice mention, bare or not, so an incident photo captioned "@huume this pipe burst" can't be hijacked. Bytes come straight from `storage.download_file(att["url"])` — the channel upload endpoint (`routes/channels.py:upload_channel_files`) writes to the PUBLIC CloudFront bucket, so no presigned-URL round trip is needed. **STRICT mode, unlike the page's `/receipts/commit`**: the confirm reply re-checks the SAME `approve_order` authz bar `_bg_inventory_reply` re-checks on its own replier (role + `inventory` flag, re-verified fresh on the REPLIER — not just whoever staged the draft) before calling `receipts.receive_channel_lines` (same writer the deterministic "we got the delivery" INVENTORY fork uses), which only ever receives against an item's own open order — nothing is auto-created from an unreviewed chat attachment, matching the provenance invariant above. A parsed multi-line receipt has nowhere to live between the review pill and the confirm reply the way a single order does, so it gets its own staging table, `inventory_receipt_drafts` (migration `receiptdraft01`) — same `confirm_message_id` atomic-claim shape as `schedule_chat_proposals`/`inventory_orders`, and `_bg_receipt_reply` slots into the SAME claim chain as `_bg_schedule_reply`/`_bg_inventory_reply` in `_bg_ems_dispatch`. Lines are RE-resolved fresh at confirm time (not trusted from the stage-time preview) — an order may have been queued or claimed by something else in the meantime.

**Injury-adjacent safety (bias-to-LOG, carried over from EMS's own invariant)**: the `INVENTORY` intent patterns are narrow `^`-anchored verb sets that deliberately exclude bare "gave"/"used" — "we gave John a written warning" and "someone used the slicer and got hurt" both stay `LOG`, never misroute into inventory. Before any inventory handling, `_bg_inventory_request` runs the deterministic OSHA-keyword check (`event_intake.fallback_classification(content).get("urgency") == "osha"`) — a hit ALSO fires `_bg_ems_intake` (dual-write, documentation never lost to a misroute). Non-actionable or failed Gemini extraction (`services/inventory/extraction.py:extract_inventory`, one JSON-mode call via `model_catalog.GEMINI_FLASH_LITE`, never raises) falls back to `_bg_ems_intake` wholesale, same as the OSHA case. A company with `inventory` off but `ems` on delegates every would-be inventory message to plain EMS logging rather than silently dropping it.

**Pills** (`services/inventory/pills.py`) always start with 📦 (never 🚨 — `systemContent.tsx` sniffs char 0 for urgent-red, so 📦 must never collide with that convention) and carry their own question-marker wire format (`_QUESTION_MARKER`/`_QUESTION_SUFFIX`, distinct from EMS's `event_intake._QUESTION_MARKER` — these are two independent round-trip formats, not shared state).

**Full manage-by-chat from Huume threads** (the `huume` flag's chat surface, not just the `/work` Inventory page): beyond the read-only `lookup_context(topic="inventory")` (items + current count + any open order, capped 20) and `show_record("inventory_item", ...)` (`services/huume/record_view.py` — item + last 10 movements + open order), five STAGED (confirm-first, like every other Huume write) tools live in `services/huume/inventory_skill.py`: `record_stock_movement` (out/stockout/adjust — NOT `in`; the tool's schema enum excludes it and `_validate_inventory_movement` refuses a smuggled one with a message steering to `decide_inventory_order(receive)` or `stage_receipt_from_attachment`, per the provenance invariant above), `decide_inventory_order` (approve/receive/cancel), `create_inventory_item`, `archive_inventory_item`, and `stage_receipt_from_attachment` (parses a CSV the admin attached to their thread message server-side — `receipts.parse_csv_bytes` + `resolve_lines`, same engine the page's parse endpoint uses — and stages the resolved lines; the model never sees or retypes line items; a duplicate-invoice warning surfaces in the staged state and the CONFIRM turn itself is the override, no separate force round-trip). A sixth tool, `stage_inventory_order`, is a plain WRITE (not staged) — queuing an order IS the staging step, mirroring `services/ems/channel_agent.py`'s channel-side tool of the same name; `decide_inventory_order` is what approves/receives/cancels it. A new `lookup_context(topic="locations")` lists the company's stores so the model can resolve a `location_id` when the admin names a store — thread callers pass ids explicitly (never fuzzy-matched names), unlike the channel path's location-binding-by-channel. All five staged action types gate on `inventory` alone via `_HUUME_ACTION_REQUIRED_FEATURE` (`services/huume/actions.py`), same single-flag pattern as `training_assign`/`pto_decision`. Approve/receive/cancel on a thread-staged order do NOT re-run `rules.evaluate_inventory_action`'s `approve_order` role check — Huume's own `_ALLOWED_ROLES` (`{client, admin}`) is already at least as strict.

`commit_receipt_lines` (the transaction-per-line writer + dup-invoice guard) and `create_item_checked`/`archive_item` live in `services/inventory/{receipts,movements}.py` as shared functions — `routes/inventory.py`'s REST endpoints and the Huume chat tools call the SAME writers, so a chat-originated write and a page-originated write are indistinguishable rows.

**Stock audit** (`services/inventory/audits.py`, `routes/inventory.py` `/audit/*`, `client/src/work/pages/InventoryAudit.tsx`, 2026-08-06): the bulk-count alternative to `ItemDetail`'s one-item-per-navigation "Set count" flow — a manager walks the store, types a count for every item they check, and saves all the changed rows in one request. `POST /inventory/audit/commit` (ships free with `inventory`, no separate flag) writes each line through `movements.adjust_item_count` (`kind='adjust'` only — same provenance invariant as everywhere else: a physical recount is a bare assertion, accepted as a correction, never a claim of a delivery) with per-line transactions (`commit_audit_lines`, mirrors `receipts.commit_receipt_lines`'s per-line-fails-alone shape) and a default `note="Stock audit"` so audit-originated rows are distinguishable in the ledger from a page or Huume-chat adjust. Untouched items are simply absent from the request — the sheet only submits rows the manager actually typed into, and a re-confirmed unchanged count (delta 0) still writes, since a confirmed count is itself audit information.

**Voice stock counts** (`inventory_voice` flag, `services/inventory/voice_audit.py`, `POST /inventory/audit/voice-parse`): optional Dictate button on the Audit sheet — one Gemini multimodal call transcribes a spoken count list ("twelve boxes of gloves, six bags of espresso beans...") and extracts `{item_name, quantity, unit}` lines, grounded against the company's own item names the same way `extraction.py`'s channel-intake prompt is (reuse an exact catalog name when the speech clearly matches one). Each line is then fuzzy-matched via `matching.best_match` (`resolve_count_lines`, read-only) so the sheet can prefill a count directly against a known item, or offer "Add as new item" for anything unmatched. **Writes nothing** — same review-then-commit shape as the CSV/PDF receipt parse and `ir_voice_intake`; the manager's Save (`/audit/commit`) is the only writer. `available` on the response means "Gemini returned a usable response" (a clean transcript that heard zero countable items is still `available=true`, `lines=[]`) — distinct from `lines` being empty, so the sheet can tell "couldn't understand the audio" (retry/type) apart from "understood, but nothing to count" (also type, different message). Both `commit_audit_lines` (`audits.py`) and `resolve_count_lines`/the route accept an optional prefetched `existing`/`catalog` list so a batch with several `new_item_name` lines, or a voice-parse call that already fetched the catalog for the grounding prompt, doesn't re-run `list_item_names` per line/call. Audio capture reuses the WAV-via-AudioWorklet stack `ir_voice_intake` established (`client/src/hooks/useVoiceDictation.ts`, hoisted out of `hooks/ir/` since it was already IR-agnostic — MediaRecorder's webm/opus isn't accepted by Gemini's audio understanding, hence the hand-rolled WAV assembly). Own rate-limit action keys (`inv_voice_parse*`) — not shared with IR voice's budget. Model: `GEMINI_FLASH` (audio tier), not `GEMINI_FLASH_LITE` (text-only channel extraction uses that one). Default off; admin-toggle; NOT bundled — `inventory` itself stays free.

**Grounded-pilots corpus wiring:** `inventory_waste` is the deliberate loss-prevention exception to the usual inventory exclusion. Analysis Pilot's `inventory_loss_monthly` platform source exposes only deterministic monthly waste and recipe-usage variance, gated by `inventory_waste`; it never exposes current stock rows or turns the legal/HR pilots into inventory readers.

**Perishable lots:** `inventory_lots` is an advisory FEFO overlay, never a second source of truth. `inventory_items.current_quantity` remains authoritative; lots label received stock, support expiry alerts and attribute discard, but are allowed to drift and never block a ledger write or reconciliation.

**Tables** (migration `inventory01`, `down_revision="ems02"`; per-location split added by `oploc01`): `inventory_items` (company-scoped, `location_id UUID REFERENCES business_locations(id) ON DELETE SET NULL`, `uniq_inventory_items_name` unique on `(company_id, location_id, normalized_name) NULLS NOT DISTINCT WHERE archived_at IS NULL` — a NULL `location_id` is one shared company-wide slot, same as the pre-`oploc01` index), `inventory_movements` (append-only, `uniq_inventory_movements_message` dedupes a WS cmid-retry, `uniq_inventory_movements_clarify` is the atomic reply-claim key), `inventory_orders` (`uniq_inventory_orders_confirm` is the atomic reply-claim key, `uniq_inventory_orders_open` enforces one queued order per item — unaffected by the location split, since it's keyed on `item_id`). Gates the `/inventory` router (`routes/inventory.py` — items/movements/orders/suggestions REST surface for the `/work` page) + the `/work`, `/werk`, and `/werk-lite` Inventory page, now grouped under the **"Ops"** sidebar heading alongside Events/Protocol. In `FEATURE_REQUIRES` (`("matcha_work",)`) — same reasoning as `ems`/`huume`: meaningless without channels to trigger from.

**Store-channel scope**: a channel bound to a `business_locations` row (`channels.location_id`) resolves and creates items scoped to that store. `movements.list_item_names(conn, company_id, location_id)` returns the store's own items plus legacy company-wide (`location_id IS NULL`) rows — so a store channel can still match an existing unscoped item, but never another store's; an unscoped channel sees only company-wide rows. `movements.find_or_create_item(..., location_id=...)` threads the same scope into the `ON CONFLICT (company_id, location_id, normalized_name)` insert arbiter. The `/work` Inventory page itself is unscoped (lists everything, with a location filter/tag) — the channel is what's store-bound, not the catalog view.

**Known v1 limitations** (documented here, not silently absent): item merge for near-duplicate auto-created items surviving fuzzy match is not offered; receipt unit conversion ("2 cases" vs "48 cookies") is not modeled — sales mappings do provide conversion for POS lines only; cross-location recommendations are read-only and do not yet create a durable transfer/paired movement workflow; `extraction.extract_inventory` has no "at the other store" override — the dispatching channel's own location scope is authoritative, an explicit other-store mention in the message text is not parsed; `receipts.py` and `sales_parse.py` reject `.xlsx`/`.xls` (export the spreadsheet as CSV first); the duplicate-invoice guard remains a `note` text match, while sales imports have a real period key; POS API support is Square-first, requires explicit external-item mapping, syncs finalized prior-day orders, and has no correction/reversal writer yet; Toast remains partner/API-access gated and intentionally has no adapter; a chat-reported delivery for an item with no open order is not auto-created and does not create one — the reporter is steered to queue an order first or use Receive Delivery (deliberate, per the provenance invariant, not an oversight). Default off; admin-toggle; NOT bundled.

**Sales intake** (`sales_intake`, migration `sales01`): POS/PMIX exports are reviewed as itemized sales lines and then written as `kind='sale'` movements. `inventory_sales_mappings` supports direct SKU conversion (`quantity_per_sale=6`) and recipe/BOM mappings; upload review can map a sold item to multiple stock components. Depletion is aggregated per stock item before one `record_movements` call. The sales import period key and `uniq_inventory_movements_sales` are real indexed duplicate guards, not `note LIKE` matching. CSV parsing is deterministic, accepts common POS header aliases, preserves negative refunds, and never calls Gemini. `GET /inventory/audit/sheet` returns current quantity plus the last-adjust baseline and movement buckets; `inventory_audit_runs` stores unit/value variance. `reorder.suggest_order` counts `sale` alongside `out` as consumption.

**Inventory forecasting** (`inventory_forecasting`, migrations `invforecast01` + `pos01`): the deterministic engine reads committed sales-import lines through the existing product-to-stock mappings. `services/inventory/forecast.py` uses weekday medians when comparable history exists, falls back to a trailing average, projects runout/order-by dates, accounts for ordered-but-not-received supply, and rounds advisory quantities to case packs/minimums. `services/inventory/forecast_store.py` persists settings, per-item replenishment rules, immutable runs, and the exact calculation snapshot. Unknown counts and sparse history never produce an order quantity; managers still approve orders through the existing order queue. Square finalized-order ingestion (`services/inventory/pos/`) normalizes through the same reviewed sales writer with explicit location/item mappings and stable external-batch idempotency. `services/inventory/forecast_ai.py` is parse-only and rate-limited: Gemini can suggest bounded weekly demand multipliers and risks, but suggestions require manager acceptance, are stored only as `ai_accepted` forecast overrides, and never write inventory or order data. Toast remains intentionally unimplemented pending partner/API access.

**Cross-location inventory intelligence** (`services/inventory/network.py`, `GET /inventory/forecast/network`): a read-only, deterministic balancing layer over per-location forecasts. Items are compared only when their stored `normalized_name` and unit match across active physical locations. A recipient's need is its lead-time-plus-safety-stock target minus current and already-ordered supply; a donor can contribute only physical current stock above its own target, never incoming stock. Both sides require `status='ready'`, so unknown counts and sparse sales history are surfaced in `attention[]` instead of being treated as transferable supply. The engine allocates the earliest order-by/runout risks first, reports full versus partial coverage, recalculates the supplier-pack-rounded remainder, and never writes a movement or order. The web Forecast page surfaces this network plan before the original reorder plan and labels affected orders "Order anyway" so the transfer option cannot be missed.

**Buying guidance — Level 1 advisory** (`services/inventory/{buying,buying_store}.py`, `/inventory/buying`, migration `invbuy01`): runs only after the saved forecast scenario and cross-location transfer plan. It does not transmit a purchase order or become the financial system of record. Supplier/item/store terms are manager-configured or learned only from a human-confirmed receipt; an unreviewed Gemini receipt draft never writes supplier evidence. The deterministic engine applies pack/minimum rounding, ranks on-time options before landed cost, marks a late best option `expedite`, and requires price confirmation when a price is missing or older than 90 days. Missing counts/history remain `count_first`. Each manager-generated plan is immutable and fingerprinted over forecast, shortages, transfers, and supplier terms. "Stage internally" re-computes that fingerprint and returns 409 on stale advice, then writes only the existing internal `inventory_orders` queue—never an external vendor transaction. CSV export is advisory. AI must never invent prices, suppliers, freight, lead times, or savings baselines.

The optional mailbox path uses one platform Gmail OAuth refresh token, not tenant-user credentials. `sales_intake_poll` is Celery-dispatched but seeded disabled and fail-closed through `scheduler_settings`; an unregistered sender stays unread, an unmapped message becomes a reviewable draft, and a fully mapped message commits with `gmail_message_id` provenance. Square API sync is a separate tenant OAuth connection (`routes/inventory_pos.py`, `services/inventory/pos/`) and is also seeded disabled; it only imports finalized orders after explicit location and external-item mapping, with stable `external_batch_id` idempotency. There is no reversal/correction writer yet, and Toast remains unimplemented pending partner access. Correcting a wrong import requires a physical audit (`adjust`).

**Waste & shrinkage** (`inventory_waste`, default ❌, requires `inventory`, migration `invwaste01`): a `waste` movement `kind` + a `waste_reason` taxonomy (`services/inventory/waste/reasons.py:WASTE_REASONS`, CHECK-constrained on the DB side — `tests/inventory/test_waste_reasons.py` pins the two in sync) so spoilage/prep-error/overproduction/breakage/contamination/comp/recall/theft/unknown stock loss is distinguishable in the ledger instead of collapsing into a free-text `out`. Delta sign is the same as `out` (`-abs(quantity)`) — waste always decreases `current_quantity`, never adjusts it back up. `services/inventory/reorder.py:suggest_order` deliberately **excludes** `waste` from its consumption rate (only `out`/`sale` count) — waste is loss, not demand, and must never inflate a reorder suggestion; it's surfaced separately as `waste_in_window` in the same return dict. `services/inventory/expected.py:expected_breakdown` buckets `wasted` alongside `received`/`sold`/`manual_out`/`stockouts` since the last count baseline. `inventory_items` also gained `category`, `shelf_life_days`, and `yield_pct` (trim/prep loss factor); the perishable-aware forecast cap and theoretical-vs-actual usage variance now consume those fields.

**Chat capture provenance invariant, extending the `kind='in'` rule above:** `waste` is a first-hand observed LOSS, same class as `out`/`adjust`/the chat `return` addition — free-form `@huume` capture needs no confirm step, because it can only ever decrement stock and therefore cannot fabricate it. `services/inventory/extraction.py`'s `_VALID_KINDS` includes `"waste"`, and `channels_ws.py:_bg_inventory_request`'s `waste` branch never auto-creates an item (`movements_service.find_item`, match-only — same bar as `return`); an unmatched name steers to the Inventory page instead of minting a catalog row from an unreviewed chat aside. A waste report also dual-writes an EMS event when that feature is enabled, so the Ops record retains the narrative while the movement ledger records the stock loss. **One deliberate exception inside the exception:** a chat-reported `waste_reason='theft'` is always coerced to `'unknown'` (`waste/reasons.py:coerce_chat_reason`, re-enforced in `extraction._coerce_result` as belt-and-braces) — a personnel accusation must never be minted by an extraction model from a Slack-style aside. The pill says so explicitly (`pills.waste_pill(..., reason_coerced=True)`) and steers to the page, where a human can record `theft` directly if that's genuinely what happened. `rules.py:evaluate_inventory_action`'s `stage="waste"` gate requires `inventory_waste` on top of the existing `stage="movement"` bar (any channel member, `inventory` only) — checked once extraction has resolved `kind == "waste"`, not before, so a company without the flag doesn't pay for a wasted Gemini call on every message.

Also fixed in this migration's PR: `movements.amend_movement_quantity`'s sign map was `-1 if kind == "out" else 1` — a `waste` movement amended through the quantity-clarify reply path would have gotten `sign = +1` and added stock back instead of correcting a deduction. Now `-1 if kind in ("out", "waste") else 1`.
