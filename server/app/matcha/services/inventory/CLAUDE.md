# Inventory (channel-driven stock tracking) — feature spec

Moved verbatim from root `CLAUDE.md`'s Feature Flags table. Root keeps a one-line summary + `→ full spec:` pointer here. Default column matches `DEFAULT_COMPANY_FEATURES` in `server/app/core/feature_flags.py`.

## `inventory` (default ❌)

**Channel-driven inventory tracking** via `@huume` in any `/work` / `/werk` / `/werk-lite` channel — "we gifted some Cherry Farms cookies to Elizabeth our manager" auto-deducts stock; "we ran out of salads again" records a stockout, runs deterministic pattern math over the item's depletion history (`services/inventory/reorder.py:suggest_order` — daily consumption rate over a 90-day lookback, average stockout interval, confidence tier; returns `None` when history is too thin to say anything useful), and stages a pending order the manager approves by replying **confirm** in-channel. Like `ems`/`schedule_chat`, the `@huume` surface here is NOT the Huume thread agent (that requires an `mw_threads` row) — it's the EMS one-shot dispatch (`server/app/werk/routes/channels_ws.py`), routed by `services/ems/intent.py`'s `INVENTORY` classification (checked after `SCHEDULE`, before `RECALL`).

**Items auto-create on first mention** — fuzzy-matched first (`services/inventory/matching.py`, stdlib `difflib`, no pg_trgm — deliberately avoided on RDS) so "cookies", "Cherry Farms Cookies!", and "cheery farms cookies" (typo) all resolve to the same row; a genuine miss inserts a new `auto_created=true` item. **Movements are an append-only ledger** (`inventory_movements`, kinds `out`/`in`/`stockout`/`adjust`) with exactly one sanctioned exception: a movement recorded with an unstated quantity ("some cookies") posts as `quantity=1, quantity_estimated=true` and arms a clarify question on the pill; a later numeric reply amends that SAME row in place (`amended_by`/`amended_at`, only while `quantity_estimated` is still true) rather than appending a correction — capped at 2 clarify rounds. `current_quantity NUMERIC NULL` on `inventory_items` means "unknown" (auto-created items start there); a deduction against an unknown count stays unknown, a `stockout` movement force-sets it to 0, and `adjust` (the only set-count path — always via `movements.adjust_item_count`, never a bare column write) establishes a real baseline.

**Orders are internal records only** — no vendor integration. Lifecycle `queued` (staged from a stockout, or created manually on the Inventory page) → `ordered` (an in-channel **confirm** reply or a page Approve click) → `received` (a page Receive action writes the restocking `in` movement) + `cancelled`. A partial unique index (`uniq_inventory_orders_open`) enforces one queued order per item; a repeat stockout re-points the SAME order's confirm pill (`orders.stage_order`'s `ON CONFLICT (item_id) WHERE status='queued' DO UPDATE`) rather than erroring or duplicating — the new system message becomes the order's `confirm_message_id`, so a reply to the earlier, superseded pill claims nothing and falls through to the mention fork (known/accepted v1 behavior).

**Injury-adjacent safety (bias-to-LOG, carried over from EMS's own invariant)**: the `INVENTORY` intent patterns are narrow `^`-anchored verb sets that deliberately exclude bare "gave"/"used" — "we gave John a written warning" and "someone used the slicer and got hurt" both stay `LOG`, never misroute into inventory. Before any inventory handling, `_bg_inventory_request` runs the deterministic OSHA-keyword check (`event_intake.fallback_classification(content).get("urgency") == "osha"`) — a hit ALSO fires `_bg_ems_intake` (dual-write, documentation never lost to a misroute). Non-actionable or failed Gemini extraction (`services/inventory/extraction.py:extract_inventory`, one JSON-mode call via `model_catalog.GEMINI_FLASH_LITE`, never raises) falls back to `_bg_ems_intake` wholesale, same as the OSHA case. A company with `inventory` off but `ems` on delegates every would-be inventory message to plain EMS logging rather than silently dropping it.

**Pills** (`services/inventory/pills.py`) always start with 📦 (never 🚨 — `systemContent.tsx` sniffs char 0 for urgent-red, so 📦 must never collide with that convention) and carry their own question-marker wire format (`_QUESTION_MARKER`/`_QUESTION_SUFFIX`, distinct from EMS's `event_intake._QUESTION_MARKER` — these are two independent round-trip formats, not shared state).

**Reachable from Huume threads too** (the `huume` flag's chat surface, not just the `/work` Inventory page): `lookup_context(topic="inventory")` lists items with current count and any open order (capped 20, same truncation-note idiom as `topic="events"`), and `show_record("inventory_item", ...)` opens one in the side panel (`services/huume/record_view.py` — item + last 10 movements + open order). No staged chat action for approving orders in v1 (channel confirm-reply and the page button are the only approval paths).

**Grounded-pilots corpus wiring is deliberately skipped.** The root CLAUDE.md's rule — "when a new analytics/risk engine lands under `services/`, the same PR wires its records into whichever grounded pilots ground on that domain" — does not apply here: inventory data is operational stock (what's in the walk-in), not compliance/legal evidence. No grounded pilot (Legal/Broker/Handbook/HR/Analysis Pilot) cites it in v1. Revisit only if a future pilot's domain genuinely needs stock-on-hand facts (e.g. a food-safety or loss-prevention angle), not as a default follow-up.

**Tables** (migration `inventory01`, `down_revision="ems02"`; per-location split added by `oploc01`): `inventory_items` (company-scoped, `location_id UUID REFERENCES business_locations(id) ON DELETE SET NULL`, `uniq_inventory_items_name` unique on `(company_id, location_id, normalized_name) NULLS NOT DISTINCT WHERE archived_at IS NULL` — a NULL `location_id` is one shared company-wide slot, same as the pre-`oploc01` index), `inventory_movements` (append-only, `uniq_inventory_movements_message` dedupes a WS cmid-retry, `uniq_inventory_movements_clarify` is the atomic reply-claim key), `inventory_orders` (`uniq_inventory_orders_confirm` is the atomic reply-claim key, `uniq_inventory_orders_open` enforces one queued order per item — unaffected by the location split, since it's keyed on `item_id`). Gates the `/inventory` router (`routes/inventory.py` — items/movements/orders/suggestions REST surface for the `/work` page) + the `/work`, `/werk`, and `/werk-lite` Inventory page, now grouped under the **"Ops"** sidebar heading alongside Events/Protocol. In `FEATURE_REQUIRES` (`("matcha_work",)`) — same reasoning as `ems`/`huume`: meaningless without channels to trigger from.

**Store-channel scope**: a channel bound to a `business_locations` row (`channels.location_id`) resolves and creates items scoped to that store. `movements.list_item_names(conn, company_id, location_id)` returns the store's own items plus legacy company-wide (`location_id IS NULL`) rows — so a store channel can still match an existing unscoped item, but never another store's; an unscoped channel sees only company-wide rows. `movements.find_or_create_item(..., location_id=...)` threads the same scope into the `ON CONFLICT (company_id, location_id, normalized_name)` insert arbiter. The `/work` Inventory page itself is unscoped (lists everything, with a location filter/tag) — the channel is what's store-bound, not the catalog view.

**Known v1 limitations** (documented here, not silently absent): item merge for near-duplicate auto-created items surviving fuzzy match is not offered; unit conversion ("2 cases" vs "48 cookies") is not modeled — quantities are tracked in whatever unit the reporter used; no cross-location stock transfer; `extraction.extract_inventory` has no "at the other store" override — the dispatching channel's own location scope is authoritative, an explicit other-store mention in the message text is not parsed. Default off; admin-toggle; NOT bundled.
