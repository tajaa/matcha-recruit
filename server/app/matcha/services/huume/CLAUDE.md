# Huume — feature spec(s)

Moved verbatim from root `CLAUDE.md`'s Feature Flags table. Root keeps a one-line summary + `→ full spec:` pointer here. Default column below matches `DEFAULT_COMPANY_FEATURES` in `server/app/core/feature_flags.py`.

## `huume` (default ❌)

**Huume** — Matcha's agentic harness inside matcha-work threads (`server/app/matcha/services/huume/`), the Matcha analog of cappe's Merlin: a **bounded Gemini tool-calling loop** (`agent.py`, 8 model calls / 300s wall clock, force-finish with partial work on a bound hit, never-raises past `RateLimitExceeded`) over a validated tool registry (`tools.py`), streamed as `step` SSE frames — distinct from every other thread mode, which only injects a context block into the single-shot skill engine. Its ThreadMode entry (`huume_mode` column) is `custom_dispatch=True`; the loop replaces the whole turn (`routes/matcha_work/messaging.py:_run_huume_dispatch`), not just a context builder. Skill #1 is **end-to-end new-hire onboarding**: draft an offer letter (`draft_offer_letter`, DRAFT-only, never sent) → `send_offer` **stages** a sign link at the public `/offer/:token` page (candidate types their name, accepts/declines — `routes/employee_lifecycle/offer_letters.py` candidate endpoints, signed PDF stored via `upload_private_file`) → on acceptance the originating thread (resolved from `offer_letters.source_thread_id`, migration `offthread01` — set once at draft time by `draft_offer_letter`/`save_offer_letter_draft` and never repointed, with the older `mw_threads.linked_offer_letter_id` reverse lookup kept only as a fallback for pre-migration rows, since that column is one slot per thread and gets silently repointed by whichever offer was drafted there most recently) gets a system notice + a bell notification to the thread creator and any `clients.is_hr_approver` users (`link=/work/{thread_id}`), inline in the accept route via `_notify_huume_thread_of_offer_event` (never-raises — `thread_id` is bound before the try body so a failure can't itself NameError out of the handler), with **no model call from the public endpoint** → `build_onboarding_plan` **stages** the full plan (employee record, portal invite, onboarding tasks, credential requirements, training assignment, Google Workspace + Slack provisioning via `services/onboarding/onboarding_orchestrator.py`, and read-only schedule/benefits/jurisdiction notes) as a checklist in `mw_threads.current_state.huume_plans`, **keyed by `offer_id`** — a thread can be mid-onboarding for several candidates at once, each with its own plan/steps, so building or executing one never touches another's. **Plan-then-approve, not auto-execute**: nothing runs until the admin approves (chat: `execute_approved_steps`, which takes an optional `offer_id` — omit only when exactly one plan is active, else name it; UI: `POST .../huume/plan/approve` + `.../plan/execute`, `routes/matcha_work/huume.py`, same `offer_id` contract) — every step re-checks its own required feature/integration at execute time (`actions.evaluate_plan_step`), and a step with a `record_id` already set is refused as "already done" (idempotent against double-clicks). Both the chat tool and the REST routes fun­nel through **one** locked executor, `store.execute_plan_locked` — a Postgres session advisory lock keyed on `(thread_id, offer_id)` (not a row lock/transaction, since plan steps call slow external provisioning) — so a chat-driven execute and a UI-button execute for the same candidate can't race and clobber each other's `record_id`s; the merge itself (`actions.merge_executed_steps`) keeps any step a concurrent caller left `approved`/`proposed` rather than overwriting it. Confirm-first for `send_offer` mirrors `hr_pilot_actions.evaluate_hr_action` exactly: a pure `evaluate_huume_action` verdict (two-turn stage/confirm, role ∈ {client,admin}, `huume`+`matcha_work`+`offer_letters` flags re-asserted — the skill engine gates nothing itself) gates every write; `evaluate_plan_execution` re-asserts the same role/flag check on the chat tool's plan-execute path specifically (the REST route already gets it from `require_admin_or_client`). The two-turn rule for plans is enforced structurally, not just by prompt: `pre_turn_plans` is a snapshot of `huume_plans` frozen **before** any tool call in the turn runs, so a plan built earlier in the same turn is absent from it — `actions.resolve_plan_offer_id` can't resolve an execute request against it, refusing with "built this turn, review and approve next message" rather than relying on the model to self-police. A `cancel_staged` tool (+ chat-only, no REST twin) voids a pending `send_offer` or discards a plan via `actions.evaluate_cancel_plan` (refused once `executing`/`done` — nothing already run can be undone from here). The system prompt embeds a **staged-state block** (`prompt.build_state_block`, rebuilt every turn from `current_state`) listing every staged action/plan and its `offer_id`s explicitly, so the model echoes real ids on a confirm turn instead of guessing; it renders "Nothing is currently staged" when empty so silence is never ambiguous. `lookup_context` also answers general grounded HR questions now — `employee`/`training_status`/`schedule`/`incidents`/`er_cases`/`credentials` topics (gated per-topic on the relevant feature flag via the same off/empty three-state idiom as `hr_pilot_corpus`; `incidents` and `er_cases` report ids/titles/status/counts within a caller-supplied `days` window (incidents, default 90/max 365) but never `involved_employee_ids`, witnesses, or narrative description — legal records). A `show_record(record_type, record_ids)` tool (`record_type` ∈ incident/er_case/employee/credential, up to 8 ids per call) opens records in the thread's right panel as a persistent **working set** rather than a single preview — `current_state.huume_records` accumulates across turns (`record_view.merge_open_records`: append, dedupe-and-refocus on a repeat show_record for the same id, drop the oldest past the 8-record cap), so asking Huume to show three things in a row keeps all three tabs open instead of only the last one. The system prompt explicitly tells the model to open records here rather than typing their fields into chat (a real failure mode: the model would otherwise paste every incident's detail into the reply, burying the conversation). `services/huume/record_view.py` has two builders per type — a name-free `_model_*` summary the tool hands back to the model (same legal-record rule as the lookup topics) and a fuller `_build_*_view` the panel fetches separately per-tab via `GET .../huume/record` under the admin's own auth (`routes/matcha_work/huume.py`, re-checks that record type's own feature flag) — normalized to one `{title, chips, meta, sections, link}` shape so a single generic `RecordViewer.tsx` renders any type; adding a record type is a backend-only change. `DELETE .../huume/record` drops one tab (no feature re-check — closing a stale entry must survive a flag flip). Writes go through the row-locked `store.update_huume_records` mid-turn, NOT `state_updates`, mirroring `huume_plans` — there are two writers now (the chat tool and the panel's close button) and `apply_update`'s wholesale top-level merge has no lock between a concurrent read and write. The `huume_turn` rate limit is 60/hr/company (`turn_pipeline.py` — raised to 200/hr when real multi-record sessions made 60 too tight, then lowered back to 60 once `show_record`'s batched `_MODEL_BATCH_BUILDERS` removed the one-id-per-call symptom that justified the raise; see that file's own comment for the full history). Attached file text (`messaging.py`'s `file_context_parts`) now reaches the loop as an extra turn part; images are still out of scope for this tool-calling path. Plan writes (`build_onboarding_plan`, `execute_approved_steps`, `cancel_staged` on a plan) go through `store.update_huume_plan`/`execute_plan_locked` directly, NOT the turn's `state_updates` dict — `state_updates` merges into `current_state` wholesale via `apply_update` at turn end, which would let a second plan clobber the first; `messaging.py`'s dispatcher re-reads the thread's `current_state` after the loop finishes so the `complete` SSE frame reflects those mid-turn writes. Run/step audit in `huume_runs`/`huume_steps` (migration `huume03` — distinct from `onboarding_runs`/`onboarding_steps`, which model one provisioning attempt against one external provider, not an agent turn's tool-call trail); the pending plan/offer intent lives in `current_state`, not those tables. `huume01`/`huume02` add the offer-letter signature columns and the `huume_mode` column respectively — no new migration for the keyed-plan shape (unreleased feature, no back-compat needed). **Pilot skills in chat**: Huume also carries the **Legal Pilot** and **Handbook Pilot** into the thread as six registry tools — `list_legal_matters`/`open_legal_matter`/`ask_legal_pilot`/`generate_legal_packet` (each gated per-call on the company's `legal_defense`) and `draft_handbook_content`/`promote_handbook_drafts` (gated on `handbook_pilot`) — via `services/huume/legal_skill.py`/`handbook_skill.py`, thin wrappers over the SAME pilot service libraries the `/app/legal-pilot`/`/app/handbook-pilot` UIs use, writing to the SAME tables: a matter opened or discussed in chat shows its transcript on the Legal Pilot page (and vice versa), each huume thread lazily owns one `handbook_pilot_sessions` row, and the active matter / session + pending-draft ids ride `current_state.huume_legal`/`huume_handbook` so the state block names real ids on later turns. Authz mirrors the routes, not the skill engine: the pure `actions.evaluate_pilot_tool` re-asserts role∈{client,admin} + `huume`+`matcha_work`+the pilot's flag on every call, handbook drafting re-applies the unpaid-Matcha-X gate (`hp.unpaid_x_reason`) and shares the UI's `handbook_pilot_chat` 40/hr rate-limit key. The two-turn rule extends to promotion (`actions.filter_promotable_drafts` + skill-side `exclude_ids`): a draft proposed THIS turn cannot be promoted THIS turn. Citations survive the chat hop — pilot results carry resolved citation records, the agent accumulates them into `huume_result.citations`, and `_run_huume_dispatch` stores them under the assistant message's `metadata.citations`/`dropped_citations` (the same keys HR Pilot uses, so `MessageBubble`'s `CitationSources` renders them with zero client changes). `_WALL_CLOCK_SECONDS` went 150→240 because these tools embed their own 90s-capped Gemini call, then 240→300 when `find_discipline_candidates` landed (its batch check is internally bounded at 100s, the single heaviest tool call in the loop today). Shared-service lifts that shipped with this (routes now delegate): `services/pilots/legal_defense/matters.py` (`load_matter`/`load_messages`/`latest_memo`/`audit_matter`; `safe_name` moved into `packet.py`) and `handbook_pilot.persist_turn`/`promote_drafts`/`unpaid_x_reason`. **HR-ops skills in chat** (`services/huume/hr_ops_skill.py`): four more STAGED actions beyond `send_offer`/`draft_discipline` — `report_incident` (`incidents`), `open_er_case` (`er_copilot`), `assign_training` (`training`), `decide_pto_request` (`time_off`), each re-checked per-call by `evaluate_huume_action` against `_HUUME_ACTION_REQUIRED_FEATURE` and executed against the SAME shared writers the routes use (`create_incident_core`, `create_case_core`, `training_assignment.assign_training`, and the new `employees/_shared.decide_pto_request_core` — a lift out of `pto_admin.handle_pto_request` that also wraps the approve path's two writes, status + `pto_balances.used_hours`, in one transaction for the first time). They deliberately do NOT reuse `hr_pilot_actions`' `ir_report`/`er_case` executors: those are hard-stop HAND-OFFS that hardcode `occurred_at=now` / `category='harassment'` / `source='hr_pilot'`, which is the wrong provenance for an admin filing deliberately — and the hard-stop classifier is deliberately NOT re-run on an incident/ER narrative, since that content is exactly what those records exist to capture (same reasoning as `_HANDOFF_ACTIONS`). All four ride the single `current_state.huume_action` slot and are table-driven in the loop (`agent._HR_OPS_TOOL_SPECS` + the pure `_build_hr_ops_staged`), matching the confirm turn on a server-minted `confirm_id` (incident/ER, no natural id at stage time) or the record's own `requirement_id`/`request_id`. `lookup_context` grew to match: `training` now returns the requirement catalog, `pto_leave` the PENDING requests with ids (the tools take ids, never names), and a new `documents` topic reports pending-signature counts by document title (never employee names, `_SIGNATURE_STALE_DAYS=7` mirroring the `hr_proactive_push` sweep). Gates the `huume` thread-mode toggle + the four REST routes (plan approve/execute, record view/close). **Skill #6: incident-triggered discipline with HR approval** (migration `discipapp01`) — `check_incident_policy` (read) runs the report-only handbook/policy check on a closed incident (`services/discipline/discipline_policy_check.py`, never adjudicates); `draft_disciplinary_action` (staged, bespoke arm like `draft_discipline`) stages a discipline record from an incident — takes `employee_id`/`incident_id` as ids, re-runs the hard-stop classifier at confirm **only when there is no `incident_id`**: with one, the conduct already reached the company through its sanctioned legal-record channel (the same asymmetry `_validate_ir_report` relies on) and the supervisor-surface `workplace_safety` patterns (`injur*`/`accident`/`bleeding`/`OSHA`) match nearly every real safety incident's own narrative, so re-gating there would refuse the flagship path outright — a **standalone** draft keeps the full hard stop, identical to `draft_discipline`. At execute it goes through `discipline_engine.issue_discipline_with_supersede(..., approval_status="pending")`, which **defers** any named remedial training to `pending_remedial_requirement_id` rather than assigning it — real training is only assigned by the later approval; `decide_disciplinary_action` (staged, table-driven via `_HR_OPS_TOOL_SPECS`, `match_key="record_id"`) approves or denies a pending record, denial requiring a ≥20-char reason. `list_pending_approvals` (read) lists the HR queue. All four live in `services/huume/discipline_skill.py`, gated via `_HUUME_ACTION_REQUIRED_FEATURE["discipline_from_incident"/"discipline_decision"] = "discipline"`. `show_record` gained a fifth, name-free `discipline` type. No REST-route or record-view change was needed beyond that — `routes/matcha_work/huume.py`'s record route already reads `RECORD_REQUIRED_FEATURE` dynamically. The Celery `discipline_policy_sweep` (`app/workers/tasks/discipline_policy_sweep.py`, scheduler row seeded disabled) is what actually finds incidents to check — it scans `ir_incidents` directly (SQL `NOT EXISTS` against its own `discipline_policy_sweep_log` ledger, one row per incident ever) and opens a pre-briefed Huume thread on a finding, notifying the **designated HR approvers** (`clients.is_hr_approver`, falling back to every client user) rather than the whole company — a finding is an approval-queue event. `check_incident_policy` is gated on the company's `handbooks` flag with the three-state idiom: without a corpus it returns `module_off`, never an empty-violations result that would read as "your handbook has nothing relevant". **Discovery entry point + per-turn model tiering**: the flagship "which incidents need disciplinary action?" question was previously unanswerable in one turn — `check_incident_policy` is one-incident-per-call with its own 60s Gemini timeout, and tool calls in a batch run serially against the loop's 8-call/240s bound, so a multi-incident scan would force-finish partway and report partial work as the answer. `find_discipline_candidates` (read) answers it in one call: `discipline_policy_check.check_incidents_against_handbook` builds the handbook/policy corpus ONCE for a batch (split out of `check_incident_against_handbook`, whose own signature/return are unchanged) and checks incidents under a concurrency limit; `discipline_skill.find_candidates` reads already-checked incidents from the stored `policy_mapping` row first (zero Gemini cost — this is also how the Celery sweep's overnight work becomes readable in chat), bounds fresh checks at `_FRESH_CHECK_CAP`, and reports the rest as `not_yet_checked` rather than folding them into "nothing found". `services/huume/routing.py` resolves a per-turn model tier (`lite`/`standard`/`deep`, `agent.py`'s planner-vs-executor `GenerateContentConfig` split) heuristically — a confirm-shaped message with something actually staged routes to zero-thinking `lite`; a message matching a tool's registered `intent_hints` (or shaped like an analytical/narrative ask) routes to `deep` (thinking hard to plan, low to execute); everything else falls back to `standard`, never the cheap tier, mirroring Merlin's own "unsure lands in the middle" rule. `HuumeTool` gained `discovery`/`intent_hints` fields (`tools.py`) that both `routing.HINT_INDEX` and a generated `prompt.build_discovery_block` read — a future "which X need attention?" skill gets deep-tier routing and prompt teaching by declaring its tool, with zero routing/prompt code. Tier rides the existing `huume_runs.token_usage` JSONB (`token_usage.tier`) — no migration. **ER Copilot bridge** (`services/huume/er_skill.py`) is the first consumer of that general pattern: `ask_er_copilot`'s `intent_hints` (`"employee relations"`, `"er case"`, `"grievance"`, …) route "I have this ER situation…" to `deep` with no bespoke code. `er_case_brief` (read, no Gemini) is a name-free summary from stored `er_cases`/`er_case_documents`/`er_case_analysis` rows; `ask_er_copilot` is the grounded tool — one Gemini call over the case's document excerpts + stored analyses + applicable jurisdiction requirements (`er_compliance_grounding.build_jurisdiction_corpus`), citation-gated the same way `discipline_policy_check` is (bare-id repair, hallucinated ids dropped). Both gate through the existing `actions.evaluate_pilot_tool` envelope (`PILOT_TOOL_REQUIRED_FEATURE["er_case_brief"/"ask_er_copilot"] = "er_copilot"`, zero new gate logic) and ride `current_state.huume_er` the way Legal Pilot rides `huume_legal`. Shipped with it: `load_guidance_context`/`build_document_excerpts`/`build_er_analyzer` lifted from `routes/er_copilot/_shared.py` into `services/er/er_case_context.py` (services must not import routes/) — `_shared.py` re-imports them under their old names, so every existing route caller and `tests/er_copilot/test_document_excerpts.py` are unaffected. **EMS bridge + IR Copilot bridge** (`services/huume/ems_skill.py` + `ir_skill.py`): `promote_ems_event` (staged, `_HUUME_ACTION_REQUIRED_FEATURE["ems_promote"]="ems"`, `ems.promote.evaluate_promote` re-run per call so chat can't promote what the Events-tab button couldn't) hands its new incident's id to `current_state.huume_ir`, which `ask_ir_copilot`/`run_incident_analysis` (`PILOT_TOOL_REQUIRED_FEATURE=["ir_copilot"]`) default to when no `incident_id` is passed. Both write into the SAME tables `/app/ir/{id}` reads (`ir_incident_ai_messages` via `ir_ai_orchestrator.persist_assistant_round`, `ir_incident_analysis` upserted `ON CONFLICT (incident_id, analysis_type)`) — a chat-originated Copilot turn or analysis run is visible, and continuable, from the incident detail page. `run_incident_analysis` releases its DB connection before the up-to-60s analyzer call and takes `refresh` to bypass the cache; `ir_skill` catches `RateLimitExceeded` explicitly in both entry points rather than either letting it escape (kills the whole turn) or folding it into a generic failure. `events` joins `lookup_context`'s topic set — narrative included (truncated), unlike `incidents`/`er_cases`, because a logged event is pre-promotion documentation typed openly in a channel, not yet the legal record those topics withhold; `show_record("ems_event", ...)` opens one in the side panel including any list-valued `doc` fields, same content the model sees. **Record-view links are surface-aware** (migration `oploc01`): `_build_ems_event_view`/`_build_inventory_item_view`'s `link` field is built via `record_view._work_base_path(conn, company_id)` (`/werk-lite` for a `werk_lite` tenant, `/work` otherwise — the same `merge_company_features` lookup `ems/urgent_notify.py` uses), not a hardcoded `/work/...` — a panel opened from a werk-lite thread now deep-links back into the werk-lite shell instead of a matcha-work path that tenant never has. Default off; admin-toggle; NOT bundled. **`_lookup_context_impl` gained an optional `location_id` kwarg** (`onboarding_skill.py`), filtering `schedule`/`incidents`/`inventory` to one `business_locations` row when given; the agent-facing `lookup_context` wrapper still never supplies it (thread callers are always company-wide), it's for `services/ems/channel_grounding.py` — see `server/app/matcha/services/ems/CLAUDE.md`'s "Channel grounding beyond ems_events" for the channel-`@huume`-only registry that reuses this same read layer. The `schedule` topic's result also now carries an `assignees` name list per shift (join through `schedule_shift_assignments`), for both thread and channel callers — a published shift's staffing is already portal-visible to the whole team.
