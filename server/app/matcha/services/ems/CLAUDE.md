# EMS (channel-logged events) — feature spec(s)

Moved verbatim from root `CLAUDE.md`'s Feature Flags table. Root keeps a one-line summary + `→ full spec:` pointer here. Default column below matches `DEFAULT_COMPANY_FEATURES` in `server/app/core/feature_flags.py`.

## `ems` (default ❌)

**Event Management System** — "@huume &lt;what happened&gt;" typed in ANY werk channel (matcha-work channels, werk-lite included) logs a structured "event": deliberately wider scope than IR — behavioral (a conduct/attitude account), safety, operational, equipment, property, guest_experience, or uncategorized. **Not the Huume agent loop** — `run_huume_turn` (`services/huume/agent.py`) hard-requires an `mw_threads` row via `store._locked_state_update`, so intake is a self-contained one-shot service (`services/ems/event_intake.py`, mirrors `services/matcha_work/ticket_draft_service.py`'s draft→promote shape, not the tool-calling loop): one JSON-mode Gemini call classifies + extracts structured `doc` fields into `ems_events`, and Huume posts a persisted confirmation back into the channel as a `message_type='system'` `channel_messages` row (migration `ems01` drops `sender_id` NOT NULL + adds the column — edit/delete/react 403 on system rows). Gemini failure still logs the event (`category='uncategorized'`, raw narrative) — documentation must survive an AI outage. Admin/client review every event in the `/work` Events tab and may **PROMOTE** one into a real IR incident (`services/ems/promote.py` → the shared `create_incident_core`, `index_people=True` — an EMS event is attributed intake, mirrors the attributed `/intake/:token` path, not the anonymous one) — AI never auto-creates the incident, same invariant as `ir_voice_intake`; promotion re-asserts role∈{client,admin} + `ems`+`incidents` per call (mirrors `services/huume/actions.py:evaluate_huume_action`). No hard-stop classifier runs on event narratives — documentation content is exactly what the record exists to capture, same reasoning as `_HANDOFF_ACTIONS`. A promoted `behavioral` event lands as a normal IR incident, so the existing incident→discipline chain (`discipline_from_incident` Huume skill, `discipline_policy_sweep`) applies with zero new discipline code. Gates the `/ems` router + the `/work` events page; promotion additionally requires `incidents`. In `FEATURE_REQUIRES` (`("matcha_work",)`) — same reasoning as `huume`: meaningless without channels to trigger from, and (unlike the OSHA/IR sub-flags) defaults False so enforcing the dependency can't break an existing company. **Reachable from Huume threads too** (`huume` flag, not just the Events tab): `lookup_context(topic="events")` lists logged events (narrative included, truncated — pre-promotion documentation, not yet the legal record `incidents`/`er_cases` topics withhold), `show_record("ems_event", ...)` opens one, and `promote_ems_event` stages the same promotion the Events-tab button runs — `services/huume/ems_skill.py:execute_promote` re-asserts the full `ems.promote.evaluate_promote` envelope per call (role/flag/status), so chat can never promote what the button couldn't. **Urgency detection** (migration `ems02`): every classify pass runs a deterministic overlay (`event_intake.apply_urgency_overlay`, OUTSIDE the try so it survives a Gemini outage) that sets `ems_events.urgency` — `'osha'` from the pure regex `ir_incident_parsing._detect_osha_reportable_keywords` (same 29 CFR 1904.39 keyword list IR uses), or `'severe'` from a dedicated model-judged bool (`severe`, distinct from `severity_hint`); an OSHA hit always wins and force-sets `incident_recommendation` + a critical/safety promote-modal prefill. `urgency` is what the channel pill's **first character** encodes (🚨 vs 📋, `event_intake._pill_emoji`) — the client's only urgency signal, since the WS payload isn't re-sent on a REST history reload (`systemContent.isUrgentSystemContent` sniffs the string). An urgent event fires `services/ems/urgent_notify.py`: in-app notification to every client contact + email to the company's protocol-designated contacts (or all admins), **never the narrative** — title/category/channel/link only. **Company protocol file** (`company_event_protocols`, one row per company): structured notify contacts (`notify_emails`/`notify_all_admins`) + free-text `incident_definition`/`culture_notes`/`corrective_actions`, edited at `GET/PUT /ems/protocol` from a new "Protocol" sidebar entry on both `/work` and `/werk-lite`. The free-text half is injected into the classify prompt (`services/ems/protocols.protocol_prompt_excerpt`) **only** when the triggering message contains "incident" (case-insensitive, `protocols.mentions_incident`) — the model then judges the event against it into `protocol_qualifies`/`protocol_reasoning`; OSHA flags irrespective of protocol.

**"Ops" branding** (migration `oploc01`): the Events/Protocol/Inventory trio is presented under an "Ops" sidebar group in `/work` and `/werk-lite` — pill/help copy says "Ops" (e.g. `event_intake._confirmation_text`'s visibility clause reads `"(visible to HR admins in Ops)"`, `ask.py`'s no-events/fallback/help copy points at "Ops"). Purely cosmetic: flag name (`ems`), table names, URL paths (`/work/events`, `/work/protocol`), and every persisted identifier (`ems_promote`, `ems_event` record type, rate-limit keys) are unchanged.

**Channel store scope**: a channel bound to a `business_locations` row (`channels.location_id`) scopes intake to that store. `channels_ws._channel_location(conn, channel_id_str)` resolves `(location_id, location_name)` for the dispatching channel — **only when the location is still `is_active`**; a deactivated store reads back as unscoped `(None, None)` (the channel's own `location_id` column is untouched, so reactivating the store resumes scoping with no re-pick needed), matching `schedule_chat_rules.apply_channel_default_location`'s same stale-binding fallthrough. `_bg_ems_intake`/`_bg_ems_clarify` pass `location_name` into `event_intake.classify_event`, which injects a `## CHANNEL STORE SCOPE` block into the classify prompt ("assume the event happened at this location unless the message explicitly names a different one" — the interpolated name is stripped of `#`/newlines first, so a hostile store name can't forge a fake section header ahead of the real message) and stamps `ems_events.location_id` via `persist_event`'s `location_id` kwarg. `_bg_ems_ask` was already channel-scoped for events; it now also resolves `location_id`/dead-store status (via `_channel_location` + `_channel_bound_to_inactive_location`) and threads both into `channel_agent.py`'s tool loop below, so a store-bound channel's schedule/incidents/inventory answers stay store-scoped, and a deactivated store's binding degrades those topics rather than answering company-wide. An unscoped channel behaves exactly as before for intake (no location block, no stamp) but reads company-wide for the loop's location-scoped topics — see the "Channel grounding beyond ems_events" paragraph below for why that's not a new disclosure. Promotion (`promote.py:promote_event`) carries the event's `location_id` forward as `create_incident_core`'s real FK, same as the location magic-link intake path — the store isn't lost at the incident boundary. Default off; admin-toggle; NOT bundled.

**Channel grounding beyond ems_events** (`services/ems/channel_agent.py` + `services/ems/channel_grounding.py`): a channel `@huume` ASK question (`_bg_ems_ask`) used to be grounded ONLY on that channel's `ems_events` — it couldn't answer "who's working tomorrow" or "any incidents this month". `channel_agent.py` answers it via a bounded Gemini tool-calling loop (≤4 model calls, ~45s wall clock — the channel-sized sibling of `services/huume/agent.py`, no `mw_threads` row involved), rather than pre-fetching every topic the asker is merely *allowed* to see: the model picks one topic per `lookup_context` tool call, driven by what the question actually asks. That choice is advisory only — every call is re-validated at `channel_grounding.run_topic_lookup` (admin gate, feature gate, location availability) before any SQL runs, so a topic the model wasn't offered (or invents anyway) is refused server-side regardless. `channel_grounding.CHANNEL_TOPICS` remains the policy registry — `ChannelTopic` rows (topic name, admin-only?, location-scoped?, help bullet, render fn) backed by `services/huume/onboarding_skill.lookup_context_impl` (public — `channel_agent.py` is a genuine second caller, not a private reach-around), reusing its per-topic feature gate (`onboarding_skill.topic_allowed`, also used by `help_lines` so a capability pill never advertises a topic the next question would refuse) and legal-record redaction. Six topics ship: `schedule`/`inventory` (broadcast to everyone — a published shift's staffing and stock levels are already team-visible, portal parity; unscoped-channel reads stay company-wide for this same reason, only a store-bound channel narrows), `incidents`/`training_status`/`credentials`/`pto_leave` (admin-only — naming people in a public channel is a deliberate disclosure the asker chooses, same posture `ask.py` already takes with `behavioral` events; `pto_leave`'s render never includes `leave_type` — who's out is team-relevant, why is not). Legal/HR-confidential topics (`er_cases`, `discipline`, `documents`, `offers`) are deliberately excluded — see `channel_grounding.py`'s own docstring for why; they stay Huume-thread-only where a single admin's own conversation, not a whole room, sees them — the same reason `channel_agent.py` carries exactly one WRITE tool, `stage_inventory_order` (reuses the channel's existing reply-to-pill confirm mechanism, `_bg_inventory_reply` — nothing executes from the loop itself), and no HR-ops staging: a public confirm pill naming an employee is precisely the leak class the excluded topics guard against.

`lookup_context_impl` gained an optional `location_id` kwarg for this (`schedule`/`incidents`/`inventory` only — the three that carry a real `location_id` column, both now tolerant of `location_id IS NULL` rows so an unstamped shift/incident doesn't silently vanish from a store-scoped answer); Huume-thread callers never pass it, so their behavior is unchanged. A channel bound to a store that's since gone inactive (`_channel_bound_to_inactive_location`, `channels_ws.py`) makes location-scoped topics refuse rather than fall through to company-wide — `_channel_location`'s `(None, None)` means "no filter" on this read path, which would otherwise be a real widening from one store's data to every store's (the opposite of the write paths, where the same `(None, None)` is a narrowing). `_bg_ems_ask`'s empty short-circuit is now "no events AND no topic reachable AND no inventory-stage capability", and the hidden-events probe (admin-only events like `behavioral` existing but filtered out) runs independent of that — a schedule-only answer still can't imply the room's `ems_events` are clean when one exists but is hidden from this asker. Adding a topic later is one new `ChannelTopic` row + a render fn — nothing else changes.

**Coverage tool** (`find_shift_coverage`, added after a live-prod report that "who can we replace X with?" got a bluffed non-answer): a second read tool alongside `lookup_context`, admin-only regardless of the `schedule` topic's own `admin_only=False` — a staffing suggestion is a judgment call, not portal-parity read access. `channel_grounding.run_coverage_lookup` is the enforcement point (mirrors `run_topic_lookup`'s posture — model's `date`/`role` args are advisory, admin/feature/location/date-range are all re-checked server-side); it calls `services/scheduling/coverage.find_coverage_candidates`, the standalone extraction of `schedule_chat.build_proposal`'s candidate-assembly steps (busy-overlap filter, availability filter, week-hours ranking, credential/training lapse annotation — deliberately no `schedule_compliance` check, since a suggestion isn't an assignment). The rendered result ends with a verbatim handoff sentence ("say `@huume schedule NAME for the ROLE on DATE`") so the model chains straight into the existing SCHEDULE-intent confirm flow — coverage itself never writes anything. The system prompt now carries a `Today is …` line (needed to turn "tomorrow" into the tool's required ISO date) and both `GenerateContentConfig`s (main loop + force-finish) got `thinking_config=ThinkingConfig(thinking_level="low")` + `max_output_tokens` raised to 2000 — the prior 600-token cap with no thinking config let gemini-flash's default thinking eat the whole budget and truncate real answers mid-sentence; never `thinking_budget=0` (hard 400 on 3.x, see `huume/routing.py`).

**Schedule-change write tool** (`propose_schedule_change`, 2026-08-05 — the NL companion to the deterministic SCHEDULE-intent fork below, added after the fork's regex couldn't anchor anaphoric/compound asks like "Dana called out for Wednesday, can you put someone else on it?"): rides `coverage_available`'s exact gate (admin + `schedule` reachable — a schedule WRITE is at least as gated as the coverage READ it usually follows). The tool takes STRUCTURED args (kind/names/dates/times, mirroring `schedule_chat`'s edit-request shape) so the loop model does the extraction — never a second Gemini call inside the tool arm, same "no pooled conn across a model call" rule `_bg_schedule_request` follows. `channel_grounding.run_schedule_change` is the enforcement point: re-asserts admin + `evaluate_schedule_proposal(stage="propose")` + the SAME `ems_schedule` 20/hr budget the regex fork spends from, then calls the SAME `schedule_chat.build_proposal`/`build_edit_proposal` the fork uses — `propose_schedule_change` is a second ENTRY POINT into that machinery, not a parallel write path. `pending_proposal_id` (new, alongside `pending_order_id`) is stamped onto `schedule_chat_proposals.confirm_message_id` by `_bg_ems_ask` exactly like an order — `_bg_schedule_reply` then owns confirm/cancel/clarify with zero new reply-handling code. To resolve "those two"/"it", `_bg_ems_ask` fetches the last 12 non-system channel messages (admin + schedule-reachable only, to avoid the query on the common case that never needs it) into a `## RECENT CHANNEL MESSAGES` block — this lives in the model's USER turn, not the system instruction (`channel_agent.answer_channel_question` prefixes it onto the question text), since any channel member can author those messages and the system prompt is where the admin-only `propose_schedule_change` tool description sits. `run_schedule_change` stages `original_content` as a reconstructed plain-English sentence from the tool's own structured args (`channel_grounding._tool_args_to_sentence`), not a bare placeholder — a clarify round's re-parse (`schedule_chat.compose_clarify_followup`) needs the real names/dates to work from, not "[via ask] {kind} request".
