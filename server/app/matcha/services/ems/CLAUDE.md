# EMS (channel-logged events) — feature spec(s)

Moved verbatim from root `CLAUDE.md`'s Feature Flags table. Root keeps a one-line summary + `→ full spec:` pointer here. Default column below matches `DEFAULT_COMPANY_FEATURES` in `server/app/core/feature_flags.py`.

## `ems` (default ❌)

**Event Management System** — "@huume &lt;what happened&gt;" typed in ANY werk channel (matcha-work channels, werk-lite included) logs a structured "event": deliberately wider scope than IR — behavioral (a conduct/attitude account), safety, operational, equipment, property, guest_experience, or uncategorized. **Not the Huume agent loop** — `run_huume_turn` (`services/huume/agent.py`) hard-requires an `mw_threads` row via `store._locked_state_update`, so intake is a self-contained one-shot service (`services/ems/event_intake.py`, mirrors `services/matcha_work/ticket_draft_service.py`'s draft→promote shape, not the tool-calling loop): one JSON-mode Gemini call classifies + extracts structured `doc` fields into `ems_events`, and Huume posts a persisted confirmation back into the channel as a `message_type='system'` `channel_messages` row (migration `ems01` drops `sender_id` NOT NULL + adds the column — edit/delete/react 403 on system rows). Gemini failure still logs the event (`category='uncategorized'`, raw narrative) — documentation must survive an AI outage. Admin/client review every event in the `/work` Events tab and may **PROMOTE** one into a real IR incident (`services/ems/promote.py` → the shared `create_incident_core`, `index_people=True` — an EMS event is attributed intake, mirrors the attributed `/intake/:token` path, not the anonymous one) — AI never auto-creates the incident, same invariant as `ir_voice_intake`; promotion re-asserts role∈{client,admin} + `ems`+`incidents` per call (mirrors `services/huume/actions.py:evaluate_huume_action`). No hard-stop classifier runs on event narratives — documentation content is exactly what the record exists to capture, same reasoning as `_HANDOFF_ACTIONS`. A promoted `behavioral` event lands as a normal IR incident, so the existing incident→discipline chain (`discipline_from_incident` Huume skill, `discipline_policy_sweep`) applies with zero new discipline code. Gates the `/ems` router + the `/work` events page; promotion additionally requires `incidents`. In `FEATURE_REQUIRES` (`("matcha_work",)`) — same reasoning as `huume`: meaningless without channels to trigger from, and (unlike the OSHA/IR sub-flags) defaults False so enforcing the dependency can't break an existing company. **Reachable from Huume threads too** (`huume` flag, not just the Events tab): `lookup_context(topic="events")` lists logged events (narrative included, truncated — pre-promotion documentation, not yet the legal record `incidents`/`er_cases` topics withhold), `show_record("ems_event", ...)` opens one, and `promote_ems_event` stages the same promotion the Events-tab button runs — `services/huume/ems_skill.py:execute_promote` re-asserts the full `ems.promote.evaluate_promote` envelope per call (role/flag/status), so chat can never promote what the button couldn't. **Urgency detection** (migration `ems02`): every classify pass runs a deterministic overlay (`event_intake.apply_urgency_overlay`, OUTSIDE the try so it survives a Gemini outage) that sets `ems_events.urgency` — `'osha'` from the pure regex `ir_incident_parsing._detect_osha_reportable_keywords` (same 29 CFR 1904.39 keyword list IR uses), or `'severe'` from a dedicated model-judged bool (`severe`, distinct from `severity_hint`); an OSHA hit always wins and force-sets `incident_recommendation` + a critical/safety promote-modal prefill. `urgency` is what the channel pill's **first character** encodes (🚨 vs 📋, `event_intake._pill_emoji`) — the client's only urgency signal, since the WS payload isn't re-sent on a REST history reload (`systemContent.isUrgentSystemContent` sniffs the string). An urgent event fires `services/ems/urgent_notify.py`: in-app notification to every client contact + email to the company's protocol-designated contacts (or all admins), **never the narrative** — title/category/channel/link only. **Company protocol file** (`company_event_protocols`, one row per company): structured notify contacts (`notify_emails`/`notify_all_admins`) + free-text `incident_definition`/`culture_notes`/`corrective_actions`, edited at `GET/PUT /ems/protocol` from a new "Protocol" sidebar entry on both `/work` and `/werk-lite`. The free-text half is injected into the classify prompt (`services/ems/protocols.protocol_prompt_excerpt`) **only** when the triggering message contains "incident" (case-insensitive, `protocols.mentions_incident`) — the model then judges the event against it into `protocol_qualifies`/`protocol_reasoning`; OSHA flags irrespective of protocol.

**"Ops" branding** (migration `oploc01`): the Events/Protocol/Inventory trio is presented under an "Ops" sidebar group in `/work` and `/werk-lite` — pill/help copy says "Ops" (e.g. `event_intake._confirmation_text`'s visibility clause reads `"(visible to HR admins in Ops)"`, `ask.py`'s no-events/fallback/help copy points at "Ops"). Purely cosmetic: flag name (`ems`), table names, URL paths (`/work/events`, `/work/protocol`), and every persisted identifier (`ems_promote`, `ems_event` record type, rate-limit keys) are unchanged.

**Channel store scope**: a channel bound to a `business_locations` row (`channels.location_id`) scopes intake to that store. `channels_ws._channel_location(conn, channel_id_str)` resolves `(location_id, location_name)` for the dispatching channel — **only when the location is still `is_active`**; a deactivated store reads back as unscoped `(None, None)` (the channel's own `location_id` column is untouched, so reactivating the store resumes scoping with no re-pick needed), matching `schedule_chat_rules.apply_channel_default_location`'s same stale-binding fallthrough. `_bg_ems_intake`/`_bg_ems_clarify` pass `location_name` into `event_intake.classify_event`, which injects a `## CHANNEL STORE SCOPE` block into the classify prompt ("assume the event happened at this location unless the message explicitly names a different one" — the interpolated name is stripped of `#`/newlines first, so a hostile store name can't forge a fake section header ahead of the real message) and stamps `ems_events.location_id` via `persist_event`'s `location_id` kwarg. `_bg_ems_ask` needs no change — it's already channel-scoped. An unscoped channel behaves exactly as before (no location block, no stamp). Promotion (`promote.py:promote_event`) carries the event's `location_id` forward as `create_incident_core`'s real FK, same as the location magic-link intake path — the store isn't lost at the incident boundary. Default off; admin-toggle; NOT bundled.
