Espresso email: viewer fix + AI quick actions + email kanban kind

Context

Espresso's Gmail "Email" sidebar section lists unread mail but tapping a row does nothing, there is no AI tooling over mail, and there is no way to hand an email task to the agent. Root cause of the tap bug: EmailView.swift:145 selectEmail() sets selectedEmailId but never calls appState.clearPrimaryNav(), and PrimaryDetailPane (App/DetailPanes.swift:26-52) routes hub flags (showProjectsHub etc.) before selectedEmailId. An EmailDetailView already exists and is simply masked.

Decisions (confirmed with user):
- Email kanban tickets run on the AutoPR lane (scripts/kanban-autopr/, Luna in msandbox) with snapshot inputs: Espresso attaches the chosen emails to the card as email-<id8>.md files; the sandbox never touches Gmail. Output = report artifact + staged_actions reply drafts approved per-send through the existing outreach flow.
- "Organize" = in-app triage only (buckets in the sidebar). No gmail.modify scope, no re-consent.
- In-viewer quick actions (summarize / draft / triage) use Gemini flash-lite, copying task_summary_service.py. Luna stays on the kanban lane.
- Web /work untouched except the kanban template row. No new DB tables or migrations (verified: mw_tasks.category has no CHECK; capabilities live in platform_settings JSON; snapshots use mw_project_files).
- Nothing autonomous sends mail. Staged sends go only through autopr_staged_action approve-per-send.

Facts found during exploration that shape the plan:
- PR #508 merged: workspace.py now has oauth_callback_router (line 31); email routes at 269–465.
- Three category allowlists must stay equal: project_task_service._ALLOWED_CATEGORIES, task_draft._TASK_DRAFT_CATEGORIES, project_agent/task_draft_agent._CATEGORIES (tests/matcha_work/test_task_categories.py), and every category must appear in the draft_ticket tool description (project_agent/tools.py:88).
- .github/workflows/kanban-autopr.yml:472 hard-codes publish-research.sh; registry publisher field is not read. Must dispatch on mode, keeping literal script paths (CI guard scripts/tests/test_ci_guards.sh greps literals).
- investigate.sh:315,316,332,333 filter prior bot uploads with ^research-(report-)? regexes — must accept email- too or round 2 re-attaches everything.
- Staged sends today (task_history.py:568) call gmail.send_email(to, subject, body) with no threading; _clean_staged_action silently drops unknown keys. So staged email replies use Re: <subject> and NO in_reply_to key; threaded staged replies are a follow-up.
- AIDraftReviewSheet is a ticket-creation sheet (MWTaskDraft), not a text editor. Need a small EmailReplySheet.
- Legacy MatchaWorkService+Agent.swift:agentDraftReply decodes {draft} but server returns {draft_id,to,subject,body} — broken since written. Leave AgentPanelView alone; new calls go through EmailService.
- gmail_service.get_message drops threadId and the RFC Message-ID header; reply_to_id is misused as both Gmail threadId and In-Reply-To. Fix in PR-A (small, tested). Only other consumer sales_intake_poll.py reads id only — additive keys safe.
- test_autopr_board_capabilities.py:26 asserts exactly {"research","outreach","browse"} — becomes four.

Ship as two PRs: PR-A (viewer fix + quick actions + Gmail threading) and PR-B (email kind end-to-end). Branch: stay on current branch unless told otherwise.
